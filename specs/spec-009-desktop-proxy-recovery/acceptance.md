# 独立验收：桌面系统代理恢复

## 最终结果
PASS（返工后，S3）。独立复核了用户登录时的无界面入口、接管与归还时序、三端原生写入路径及下列首轮问题；未改动业务代码或员工系统代理。

- **Windows**：LAN 和每个 RAS/VPN 连接分别保存、核对及恢复。再次登录只遍历接管记录；后来新增的连接不参与，已删除的不重建，第三方改动一条不会阻止其余连接归还。
- **Linux**：KDE 与 GSettings 分开保存，按各自设置环境读取和比对。一方被其他应用更改时保留该更改，另一方仍可归还。多处写入途中失败会处理已完成的本次写入，未能确认的恢复保留记录。
- **macOS**：特权服务启动、停止及设置代理的路径均先检查可能受影响的已有网络服务，而非假定 RPC 一定修改请求发出时的活动接口。调度前复核服务列表和配置。会被清理影响的配置要求可还原；对于清理前后等效的直连配置，单纯启动内核不要求代理写权限。若存在无人值守进程无权还原的公司 PAC、备用地址或绕过列表，宁可在调用前停止，不抹掉这些设置。

复核证据：返工后的 12 个恢复模块用例、相关 41 个定向用例、6 个隔离的跨进程场景、macOS 实际可执行文件在无记录时的无界面运行、Windows 目标的适配器及测试编译、Linux 私有 GSettings 的 2 项检查。未把定向验证当作完整的 Windows、macOS、Linux 真机关机和重登录验收。

剩余边界：现有 macOS 特权服务在 RPC 内自行选择网络，不能按 UUID 锁定写入。请求期间才新建的网络服务，或另一应用在同一瞬间写入相同配置，无法事先保存或可靠区分；已存在服务之间的普通切换已纳入预检。安装包发布前仍宜使用测试机做断电后重新登录的实测。

## 首轮结果（历史）
FAIL（第一轮，S3）。未修改业务代码或本机系统设置。

### 已确认
登录恢复入口在 GUI 和 Tokio 初始化之前；接管记录先于原生写入落盘。已审查进程锁、未完成写入、原设置与最后写入值的比较，以及三端登录触发方式。现有证据包含 41 个 Rust 定向用例、隔离配置下的六个跨进程场景、Windows 目标适配器编译与 GSettings 私有配置测试；均不等同于三端真机关机、登录验证。

### 当时需返工
- Windows 把 LAN 和整个 RAS/VPN 电话簿视为一个设置。仅新增、移除或编辑一条 VPN 连接，就使整张已确认快照失配。释放逻辑随后删除唯一记录，仍指向已停止本机端口的 LAN 不会还原。应按连接保留与还原仍归本程序设置的项，不覆盖新连接、第三方改动或已经删除的连接。
- Plasma 下 KDE 与 GTK 使用不同设置存储。只更改其中之一，会触发同样的整条放弃逻辑，使另一套设置遗留死代理。两套存储需要独立判断归属和恢复。
- macOS 特权服务在 RPC 执行时选择网络服务；现在只预检请求开始时识别的活动服务。若开始时无网络，或请求期间从 Wi-Fi 切到设有受保护 PAC 的以太网，服务可能清空一个未验证有还原权限的配置。结束时记录错误和保留凭据不能还原被策略禁止写入的配置。应固定写入作用域或在调度前保护所有可能被覆盖的有效配置；普通直连的内核启动不应因此要求改代理权限。

实现定位：`proxy_recovery/windows.rs` 的单一 `SCOPE`/整表比较、`proxy_recovery/linux.rs` 的复合 `State`，以及 `reconcile.rs::release_scope` 的失配删除分支；macOS 为 `service_clear.rs::Transition::prepare` 和 `around_service_clear`。

复验应覆盖各自的独立设置存储发生变化，以及特权调用前后网络身份和权限不同的情况。
